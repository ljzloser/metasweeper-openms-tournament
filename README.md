# OpenMS 比赛

独立的元扫雷插件：查看 OpenMS 正在进行和即将开始的比赛，查看本人的打卡状态和倒计时，
登录后可开始打卡；也能复制比赛标识，或在下一局开始前直接设置到元扫雷，并可开启自动上传比赛录像。
支持 OpenMS 用户名、密码与图片验证码登录，登录后自动使用当前账号的用户 ID。

OpenMS 网络请求直接使用插件管理器内置的 `requests`，不使用生成的
OpenAPI SDK，也不依赖「开源扫雷网」服务插件。插件加载、设置保存和主程序通信
使用元扫雷随附的 `BasePlugin` 接口。可选的持久登录使用随包提供的 `keyring`；
插件管理器会按 `requirements.txt` 管理此依赖。

## 安装

需要支持 `SetRaceIdentifierCommand` 的元扫雷版本。

把本仓库的 `openms_tournament/` 目录放入元扫雷的 `plugins/` 或
`user_plugins/`，在插件管理器中启用「OpenMS 比赛」。如需持久登录，在插件管理器中
安装插件附带的 `requirements.txt` 依赖。也可以在本仓库执行
`python scripts/build_zip.py`，然后从插件管理器导入生成的 ZIP。

源代码托管于 [GitHub](https://github.com/ljzloser/metasweeper-openms-tournament)。

## 使用

1. 未登录时可填写 **OpenMS 用户 ID**，点击「保存并刷新」。也可以在插件设置中
   配置同名字段。这里填写 OpenMS 个人主页对应的数字用户 ID；0 表示未配置。
2. 列表显示进行中和待开始的比赛，所有时间使用北京时间（UTC+8）。
3. 列表「比赛标识」列展示每场个人标识，双击标识可复制；选中进行中的比赛可读取个人参赛时间。
4. 「我已打卡」显示参赛状态；登录后可点「一键打卡所有可参加比赛」。确认框会列出本次
   未打卡的进行中比赛；逐场提交并显示部分成功/失败，因为打卡会立即开始个人计时且不能撤回。
   周赛和效率周赛最多有两小时录像上传窗口，GSC 按比赛结束时间计算。倒计时每秒刷新。
5. 选择一场当前有效参赛的比赛后，点击「设置到元扫雷」会重新核对所有正在进行且个人
   参赛时间有效的比赛，并将它们的 token 按比赛列表顺序用英文半角逗号连接，不加空格。
   这适用于同时参加多个比赛的情况；每场比赛仍按 OpenMS 自己的参赛时间和计分规则处理，
   详见 [OpenMS 比赛标识说明](https://openms.top/docs/zh/guide/identifier#tournament-token)。
6. 表格下方的「当前总比赛标识」显示主程序当前实际设置的完整标识，可复制。 「自动维护比赛标识」默认打开：每 5 分钟刷新 OpenMS 比赛和参赛状态；一旦在个人参赛时间内
   获得标识，就会在主程序待开局（`ready`）且标识不一致时自动应用。主程序游戏状态、模式和设置
   通过本地只读查询每 3 秒更新；游戏状态变化时立即复查。自动维护不会替用户打卡。
7. 按 OpenMS 文档，插件始终把所有当前有效的参赛标识用半角逗号连接。批量打卡完成后会把所有
   有效标识设入主程序。
8. 双击表格里的标识可复制单场 `token`；下方「复制」按钮复制主程序当前总标识。如需设置，先在插件管理器的
   「控制授权」中把「设置比赛标识」授权给本插件。自动和手动设置都只在元扫雷待开局时执行；
   设置成功后保存到主程序配置，可以开始下一局，主程序不会重开棋盘。
9. 页面顶部只在未授权时显示授权提示；发现当前对局不公平、不是标准模式、启用了局面约束或作弊控制时，
   在同一区域显示简短警示按钮，点击查看原因和处理方案。两项正常时整行隐藏，不占用空间。
   插件不自动调整游戏设置，准备状态不把尚未开始的对局判为不公平。

列表查询与读取标识不需要登录。打卡要求登录且 OpenMS 账号满足实名或玩家认证条件；
自动上传默认关闭，按下文开启。若已有参赛记录，仍可直接读取标识。

## 比赛录像上传

登录后勾选「自动上传比赛录像」。插件读取元扫雷游戏结束事件的原始 EVF 数据，仅将开启后完成的
标准模式、公平且正式的胜局加入队列，并检查该局比赛标识匹配当前账号已打卡且仍在有效窗口内的比赛。
一个录像包含多场比赛标识时只上传一次，比赛是否计分和最终审核状态由 OpenMS 判定。
上传不需要主程序控制授权，也不依赖主程序是否开启自动保存录像；不修改主程序。

- 复用已登录的 `requests.Session`，直接调用 `POST /api/common/uploadvideo`，不使用 OpenAPI SDK。
- 串行处理，与比赛查询和登录请求互斥；相邻上传至少间隔一秒。OpenMS 每五分钟刷新不影响即时上传。
- 服务器返回 `file / collision` 时记为「网站已存在」，立即清空队列中的录像副本，永久结束本次任务；
  手动重试和重启插件都不会重新发送该任务。不删除主程序保存的录像文件。
- 待传数据保存在插件数据目录的 `uploads.sqlite3`；中断后可恢复。普通网络错误最多自动尝试三次；
  429 限流等待服务器冷却时间，不消耗普通失败重试次数，到参赛截止时间后仍会删除任务。
  失败项可以在「上传记录」中手动重试。登录失效时暂停，重新登录原账号后恢复；不跨账号上传待传录像。
- 超过所有匹配比赛的个人上传窗口时，不再发送，直接删除该条数据和记录。网站以实际上传时间匹配参赛窗口，
  在截止前打完但之后才上传，仍可能不计分。
- 「上传记录」只保留当前比赛范围内的成功、已存在、失败和待传项；成功记录显示网站录像 ID 和审核状态，可以打开网站录像。
  玩家标识不匹配、待审核等状态不会显示为「已计入比赛」。
- 上传成功后，插件页面最上方会单行显示录像编号、对局结果、难度、用时、3BV 和网站状态。页面可见时开始计时，5 秒后自动隐藏。旧队列缺少的字段会省略。
- 每次成功刷新比赛列表后，删除所有不再关联当前进行中或待开始比赛的上传条目，包括录像副本、哈希、网站 ID、
  成功/重复/失败等状态；一份录像关联多场比赛时，只要还有一场在范围内就保留。没有当前比赛时清空全部上传条目。
  不再按 500 条或固定天数保留历史。旧版本记录会尝试按当前账号比赛标识关联，无法关联的条目也会删除。
- 已知上传截止时间的清理每秒在本机检查，启动时也执行，不依赖登录或自动上传开关。
  关闭两项自动功能后，只要还存有上传记录，仍每五分钟刷新比赛范围；联网失败不会当作空比赛列表进行清空。
  SQLite 启用安全删除和自动空间回收，删除后数据库只保留当前比赛的数据及空表结构，不修改主程序录像文件。

所有自动化测试都拦截真实 `requests` HTTP 发送，只使用模拟会话，不会向网站上传测试录像。

## 我的比赛成绩

登录后点击进行中比赛所在行的「我的成绩」，或双击该行。双击已公开的比赛标识仍会复制标识。
个人参赛窗口已经结束时，只要整场比赛还在当前列表中，
仍可查询本人已提交的录像。只能读取当前登录账号，不使用手动填写的其他用户 ID。
窗口提供「计分明细」「已提交录像」，金羊杯另有「参考指标」。计分明细左侧显示当前成绩，右侧显示预计成绩和各局来源。
比赛列表会为已打卡的进行中比赛显示本人的「当前成绩」和「预计成绩」，并随比赛刷新更新。
双击计分项或录像行可在元扫雷中播放。有本地录像时直接播放，已有网站录像 ID 时也可下载到临时目录播放。

| 类型 | 计分方式 | 展示内容 |
|---|---|---|
| 竞速周赛 | 最快 5 局中级 + 2 局高级，缺项按 60 / 240 秒补足 | 总用时、各难度小计、取用录像及补位 |
| 效率周赛 | 每局 `用时（秒）/ IOE²`，其中 `IOE = 3BV / 点击数`；取最低 5 中 + 2 高，缺项按 60 / 240 补足 | 总分、每局用时、IOE、效率分和补位；原始精度排序，显示三位小数 |
| 金羊杯 | 最快 20 初 + 12 中 + 5 高，3BV 下限 10 / 30 / 100，缺项按 10 / 60 / 240 秒补足 | 总用时、分项计分明细；独立按最高 3BV/s 和 STNB 选取的参考统计 |

只计入网站状态为「审核通过」的标准模式录像，且单局计分须低于相应补位上限。
「已提交录像」逐局注明计入、未进入取用名额、待审核、玩家标识不匹配、非标准模式、3BV 未达标等原因。
当前成绩使用 `GET /api/tournament/get_videos/participant` 返回且审核通过的网站关联录像。
预计成绩只读取本插件自己的数据库，记录比赛进行期间与当前账号个人比赛标识匹配的胜局，即使关闭了自动上传。
按赛制的难度、取用局数、计分公式和补位规则计算，忽略对局模式、公平状态、资格门槛、上传和审核状态。
只有本地对局数据也能计算预计成绩。旧版本如果只保存了上传编号，刷新成绩时会按本地上传编号、账号及比赛
补齐缺失的计分数据，补齐后保存在本地。已经清理且未留下上传编号的旧数据无法补录。比赛结束后清理对应记录。
结果是当前网站录像的计算快照，不代表最终结算，也不显示其他人的成绩或排名预测。
可点击「刷新我的成绩」重新读取；网站读取失败时仍可查看本地预计成绩。
分析结果不写数据库；切换账号、退出登录或比赛退出当前列表时清空窗口内容。

## 账号密码登录

1. 点击主界面的「登录 OpenMS」，在登录对话框中填写用户名和密码。
2. 点击「刷新验证码」，手动填写图片中的验证码，然后点击「登录」。
3. 插件使用官网的 `POST /userprofile/login/` 提交表单，成功后通过
   `GET /api/common/loginauto` 再次核对 Cookie 会话。
4. 登录后自动保存当前账号的数字用户 ID，并锁定界面的用户 ID 输入框；
   之后选中比赛即可读取自己的参赛信息。
5. 「检查登录状态」可检测会话是否过期；「退出登录」调用官网退出接口并清除本地会话。

插件设置里的「保持登录天数」是整数输入，范围 7–90，默认 30 天；也可设置
默认用户名。选择有效天数后，会将 Cookie 存入系统安全凭据库（Windows Credential Manager、macOS
Keychain 或 Linux Secret Service），并在下次启动时验证。官网会话可能提前失效，届时插件
会删除过期会话并显示未登录。点击退出登录会删除凭据库中的 Cookie。
修改有效天数后需重新登录，新的服务器会话期限才会生效。
密码不会保存，提交后立即清空输入框。需要插件管理器安装随包提供的 `keyring` 依赖；
若系统未配置凭据库，插件会提示无法保持登录。验证码不进行自动识别；验证码错误、过期
或密码错误后，需要重新刷新图片再试。

退出时如果网络异常，本地 Cookie 仍会清除；界面会提示服务端退出尚未确认。
不登录仍可用手动用户 ID 浏览比赛和读取公开参赛信息。

登录地址属于旧版 Django 视图，**未出现在 Ninja OpenAPI JSON 中**。
实现依据公开的 [后端登录视图](https://github.com/eee555/saolei_website/blob/c2f65ec50cf3786fdfd2d88f2c5badee8bd98bb8/back_end/saolei/userprofile/views.py#L23)、
[路由](https://github.com/eee555/saolei_website/blob/c2f65ec50cf3786fdfd2d88f2c5badee8bd98bb8/back_end/saolei/userprofile/urls.py#L6)
和 [官网登录表单](https://github.com/eee555/saolei_website/blob/c2f65ec50cf3786fdfd2d88f2c5badee8bd98bb8/front_end/src/components/Login/LoginForm.vue#L102)。

## 配置与行为

| 配置 | 默认 | 说明 |
|---|---|---|
| OpenMS 用户 ID | 0 | 按该数字用户 ID 匹配参赛记录；0 表示未配置 |
| 请求超时（秒） | 8 | 每次 HTTP 请求的超时，范围 3–30 秒 |
| OpenMS 用户名 | 空 | 登录后保存，便于下次填写 |
| 保持登录天数 | 30 天 | 整数范围 7–90，不关闭持久登录 |
| 自动维护比赛标识 | 开 | 每 5 分钟检查 OpenMS，并在待开局时应用不匹配的有效标识 |
| 自动上传比赛录像 | 关 | 上传开启后完成的合格比赛胜局，网站已存在时丢弃队列副本 |

- OpenMS 网络轮询每 5 分钟一次；主程序状态只通过本机查询每 3 秒更新，不请求 OpenMS。
- 自动维护不会在没有有效参赛标识时清空主程序已有标识；登录失效或网络异常时保留当前值。
- 配置由插件管理器保存到本插件的数据目录；不在代码或仓库中记录个人标识。
- 修改用户 ID 后，之前的参赛标识会失效；需要重新选择比赛获取。
- 登录期间以服务端验证的当前用户 ID 为准，设置页中的手动 ID 不会切换登录身份。
- 仅对自己的参赛记录提供应用按钮；未开始、已结束或个人参赛窗口结束时不能应用。
- 应用前再次请求参赛记录，核对有效时间和标识，并检查独立控制授权。
- OpenMS 网络操作在后台线程执行；自动轮询不会取消打卡等正在进行的请求。
- 复制、查看无需控制授权；主进程不额外检查本插件的授权文件或作弊开关。

## 直接使用的接口

| 方法与路径 | 用途 |
|---|---|
| `GET /api/tournament/get_list?category=normal` | 一次批量取得正常比赛的完整详情，按时间划分进行中/待开始，过滤已结束比赛 |
| `GET /api/tournament/participants?tournament_id=…` | 按用户匹配参赛记录，读取 `token` |
| `GET /api/tournament/get_videos/participant?tournament_id=…&user_id=…` | 登录后读取本人已提交的比赛录像，计算个人成绩 |
| `POST /api/tournament/weekly/participant` | 周赛打卡 |
| `POST /api/tournament/weekly-eff/participant` | 效率周赛打卡 |
| `POST /api/tournament/gsc/participant` | GSC 打卡 |
| `POST /api/common/uploadvideo` | 使用登录 Cookie 和 multipart 文件字段 `file` 上传 EVF |
| `GET /userprofile/refresh_captcha/` | 获取图片验证码 key |
| `GET /userprofile/captcha/image/{hashkey}/` | 下载验证码图片，供用户手动填写 |
| `POST /userprofile/login/` | 提交用户名、密码、验证码、key 和会话过期时间 |
| `GET /api/common/loginauto` | 验证当前 Cookie 会话，读取登录用户 |
| `GET /userprofile/logout/` | 按官网旧版接口退出当前会话 |

比赛查询是公开接口；服务端权限或数据格式变更时，插件会显示错误，不回退到其他人的记录。

## 请求限流与批量能力（2026-11-21 核对）

根据网站公开源码和在线 OpenAPI，当前实际使用的接口如下。未声明专用限流不代表部署层没有其他限制。

| 接口 | 源码声明的专用限流 | 批量与复用方式 |
|---|---|---|
| `POST /api/common/uploadvideo` | 每 IP `5/s` | 只接收一个 `file`，不支持批量上传；插件逐份串行 |
| `GET /api/common/loginauto` | 每 IP `5/s` | 一次取得当前账号；不在每次上传前重复验证 |
| `GET /api/tournament/get_list?category=normal` | 未声明 | 一次返回正常比赛全部详情；替代 `get_news` + 历史全量列表 + 逐场详情查询 |
| `GET /api/tournament/participants` | 未声明 | 一次返回一场的全部参赛者，本地按用户 ID 匹配；不支持跨比赛批量 |
| `GET /api/tournament/get_videos/participant` | 未声明 | 一次返回本人该场全部录像，个人成绩不逐录像调用详情接口 |
| `POST /api/tournament/weekly/participant` | 未声明 | 不支持多场批量；直接读取返回的完整参赛记录，省掉一次 GET |
| `POST /api/tournament/weekly-eff/participant` | 每用户 `30/m` | 同上；同接口请求至少间隔 2.1 秒 |
| `POST /api/tournament/gsc/participant` | 未声明 | 无完整参赛记录，提交后查询一次确认；不支持批量 |
| `POST /userprofile/login/` | 每 IP `60/h` | 仅由用户触发；本地累计一小时调用数，达到上限不再发出 |
| `GET /userprofile/refresh_captcha/` | 每 IP `60/h` | 同样控制本地小时调用数，验证码不自动识别 |
| `GET /userprofile/captcha/image/{key}/` | 在所查路由未声明专用限流 | 取 key 后下载一次图片 |
| `GET /userprofile/logout/` | 未声明 | 用户触发，随后清除本机会话和查询缓存 |

网站的 `/api/video/staticdetailbatch`、`infobulk`、`detailbulk` 等用于已知录像 ID 的批量详情，
不能代替上传、跨比赛打卡或本人比赛录像列表；当前分析所需字段已经由列表一次返回，不再额外查询。

插件所有 HTTP 请求统一至少间隔一秒，在后台串行执行。比赛列表/成绩查询缓存三秒、参赛者查询缓存两秒，
仅合并短时间重复操作；写请求和会话变化清除缓存，设置标识前的参赛记录复查强制联网，避免使用过期标识。
收到 HTTP 429 后整个会话暂停真实网络请求，支持 `Retry-After` 的秒数和 HTTP 日期；
未给出有效头时按 30、60、120、240、300 秒退避。冷却期间不进行循环等待或重复探测，上传定时器到期再调度。
一键打卡遇到限流会保留已完成结果并停止后续提交，冷却后由用户重新操作，避免自动开始剩余比赛的计时。
限流额度可能由同 IP 的网页或其他客户端共同消耗，因此不能保证绝无 429，但会遵守服务器冷却要求。
